## Обязательность полей и фактическое создание через интерфейс

| Модель и поле | null | blank | Объявленный default | API / интерфейс | Импортёр |
| --- | --- | --- | --- | --- | --- |
| Group.study_days | False | False | отсутствует | ChoiceField required=True, allow_blank=False, allow_null=False; GroupsPage требует выбор | существующее значение или decisions.classes[class_name].study_days; иначе missing_study_days |
| StudentProfile.parent_name | False | False | отсутствует | required=True, allow_blank=False, allow_null=False; StudentsPage требует имя | существующее имя или decisions.students[login].parent_name; иначе missing_parent_name; full_clean проверяет длину 100 |
| StudentProfile.group | False | False | отсутствует | required=True, allow_null=False; для колледжа frontend отправляет college_groups[0] | существующая группа или явно согласованный primary_class, входящий в предметные группы потока |
| StudentProfile.college_groups | M2M, null неприменим | True | отсутствует | формально required=False; validate требует непустой список при создании колледжного студента | все предметные группы потока, без удаления существующих связей |
| StudentProfile.college_course | False | True | отсутствует | API допускает пустую строку; frontend требует выбрать курс | пустая строка разрешена; цифры в названии потока не трактуются как курс |
| StudentProfile.parent_phone | False | False | отсутствует | обязательный CharField с модельным валидатором телефона; форма требует номер | full_clean, исходный номер либо явно согласованный decisions.students[login].parent_phone |

У строковых полей без объявленного default Django при создании экземпляра
может получить пустую строку. PostgreSQL NOT NULL не запрещает `''`, а
`save()` сам по себе не вызывает full_clean. Поэтому техническая запись
пустого parent_name или study_days через ORM возможна, но нарушает модельную
валидацию, API и форму; импортёр не должен маскировать это как допустимые данные.
`group_id` действительно обязателен на уровне БД и имеет внешний ключ.
Choices для дней и оценок проверяются Django/API; это не эквивалент SQL CHECK.

В GroupViewSet.perform_create есть fallback MON_FRI для колледжа, и миграция
0009 выставляла MON_FRI существовавшим колледжным группам. Однако обычный POST
без study_days или с пустой строкой отклоняется GroupWriteSerializer до
perform_create. Это подтверждено интроспекцией действующего сериализатора и
тестом. Форма GroupsPage тоже требует выбор. Автоматическая подстановка
MON_FRI импортёром сейчас была бы новым допущением, а не повторением реально
доступного пути создания. Возможные решения: подтвердить MON_FRI для всех
24 классов или передать расписание по каждому классу. API здесь не исправлялся.

Имя родителя действительно обязательно во всех трёх слоях. Решение: получить
имена либо отдельно согласовать необязательность поля с изменением модели
`blank=True`, сериализатора/интерфейса и миграцией состояния. `null=True` для
хранения пустой строки не требуется. Такой переход не выполнен; фиктивные
имена и имя студента вместо родителя не используются.

Отдельного поля primary_class в модели/API нет — это имя параметра решений
импортёра. Интерфейс берёт первый выбранный предмет; MultiSelectField добавляет
предметы в порядке кликов, а не по семантическому приоритету. JSON не сообщает
порядок пользовательского выбора или основной предмет. Указание primary_class
— дополнительное требование импортёра, предотвращающее произвольный выбор.
Можно согласовать основной предмет для каждого из шести потоков либо дать
индивидуальное соответствие. Самостоятельно порядок JSON не использовался.

Требование разрешить все четыре предметные группы до создания профиля —
консервативное правило импортёра. API требует минимум одну. Оно удерживает
студента от частичного импорта состава групп и соответствует текущей цели
полного импорта. Отсутствие строки оценки само по себе не запрещает создать
профиль/членство, если остальные поля разрешены.

Дополнительная проверка без зависимости от расписаний/имён выявила 103
невалидных parent_phone; API отклоняет те же 103 значения. PHONENUMBER_DEFAULT_REGION
не задан. После выделения цифр: 83 номера из 9 цифр, 20 из 11; есть пробелы,
дефисы, NBSP и U+202C. Это описание формата, не разрешение преобразовывать
номера. Нужны страны/коды или проверенные международные номера. Не следует
автоматически назначать всем +996 или +7. Проверено 103 точных логина студентов:
существующих совпадений, коллизий регистра и точных имён с другим логином не
найдено. Сами персональные значения в этот документ не включены.

## Почему classes — это Group

В приложении нет отдельных моделей Subject, Class или потока колледжа.
Group содержит course_name, mentor и organization_type; Lesson принадлежит
одной Group. Поэтому 24 classes из JSON соответствуют 24 Group с названиями
вида «поток-предмет», а 6 groups JSON задают состав потоков и не превращаются
в дополнительные 6 предметных групп.

Один StudentProfile связан с четырьмя предметными Group через M2M
college_groups; таблица связи — tabel_app_studentprofile_college_groups,
обратная связь — Group.college_students. Это 103 профиля и 412 связей,
а не 412 разных студентов. Gradebook, список/счётчик студентов группы,
индивидуальный табель и отчёт по колледжу используют эту связь. LessonRecord
ссылается на единый профиль студента и Lesson конкретной предметной группы.

Основная group — прежняя одиночная связь, которую код продолжает использовать:
название группы в сводках, основной ментор в payload, fallback при пустом M2M,
выбор последнего урока для обычного месячного отчёта. Содержание отчёта колледжа
собирается по нескольким предметам, но get_student_trigger_lesson и
send_student_month_report ориентируются на student.group. При изменении group
через StudentProfileSerializer.update также вызывается move_student_records_to_group.
Поэтому выбор основной группы не является безразличной технической формальностью.

Дата модели Lesson имеет default timezone.localdate, но использование его
для исторической ячейки без даты выдумало бы дату урока. Поэтому импортёр
намеренно требует реальную дату. Годы 2025/2026 в корректных датах сохраняются.

Для полного сохранения без навязывания общей шкалы разумен отдельный слой
исходных ячеек: идентификатор/хеш источника, класс, строка, колонка, заголовок,
исходное значение, nullable ссылка на студента/урок, статус разрешения;
уникальность по идентификатору источника + классу + строке + колонке. Это
позволит сохранить и ячейки без дат/сопоставления. Для показа/анализа таких
результатов в интерфейсе потребуется дальнейшее расширение предметной модели.
Текущий comment не решает задачу: LessonRecord всё равно требует реальный
урок и допустимую оценку. Схема сейчас не изменялась.

## Изменения импортёра и повторный dry-run

- Нормализация краевых пробелов оценки совпадает с save_gradebook_entries.
- Пустая ячейка явно учтена в отчёте и никогда не удаляет существующую оценку.
- В отчёт добавлены точные причины неподдерживаемых ячеек и все причины
  зависимостей студента; формат телефона проверяется до блокировки зависимостей.
- Файл decisions допускает явный проверенный parent_phone; автоматических
  преобразований номеров нет. Конфликтующее существующее значение не меняется.
- Расписания, родители, основные группы, даты и значения оценок не придуманы.

Отчёт: /tmp/college-import-reviewed-dry-run-20260907.json (0600, вне Git).
Повторный dry-run: 6 User, 6 MentorProfile, 6 UserOrganizationAccess; остальные
новые записи 0. 24 класса и 103 студента заблокированы. У всех 103 студентов
одновременно отсутствуют parent_name/primary_class, не разрешены classes,
невалиден parent_phone. 2608 неподдерживаемых ячеек, 1 явно пустая, 2175
допустимых по форме записей ждут зависимостей, 32 несопоставленные строки.
Студенты и группы не стали доступны к импорту только от исправления strip.

Все 11 тестов импортёра прошли в отдельном контейнере без сети, SQLite в памяти.
Проверены обязательность API-полей, нормализация пробелов, сохранность старой
оценки при пустой ячейке, диагностика телефона, идемпотентность, пароли, сигналы
и откат. Общий backend-набор в этом уточнении повторно не запускался: ранее
обнаруженный сбой теста месячного отчёта воспроизводился на исходном образе.

Следующий шаг — согласовать недостающие значения/трактовки и способ хранения
исходных результатов, затем реализовать согласованный полный план и новый
dry-run. Импорт только менторов не считается достижением цели. До применения
по-прежнему нужны отдельное решение и свежий проверенный backup.
